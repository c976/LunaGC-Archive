# 7.1 protocol generation

The base 7.1 protocol schema is stored as `protocol/7.1/protocol.desc` with its file list in `protocol/7.1/files.txt`. The descriptor set was captured from the previously checked-in 7.1 generated Java descriptors. Its SHA-256 is `dfc0fe457558b86d661b24f0c0ac023a39bbbc37b95a35e603deb4c7efbedfa5`, and it contains 2059 protocol files. Later name recoveries (for example the GamblingChess, LunaRiteV2, SnowBallFight, VineManRun, RogueBall and SummonBattle activity messages) rename messages, fields and files in place; field numbers, labels and types are left untouched. Two activity fields were renumbered to match what the 7.1 client reads and writes: `GetActivityInfoReq.activity_id_list` is field 14 (was 4), and `ActivityInfo.meet_cond_list` is field 1917, swapping names with `quick_open_pre_quest_list` on field 13.

`protocol/7.1/compat` contains protocol files recovered after that descriptor set was captured, plus legacy protocol files required by those additions but absent from the base descriptor set. The original supplemental schemas were recovered from the `descriptorData` embedded in the corresponding generated Java classes. Native wire corrections can also replace stale base descriptors through matching file names.

`AbilityActionGenerateElemBall.proto` overrides the stale base descriptor with position on field 11 and rotation on field 14. Captured Arlecchino and Kazuha 7.1 skill packets carry these length-delimited Vector fields; the old schema used position on field 1, rotation on field 7, and an unverified `uint32 room_id` on field 14. The old parser silently retained the vectors as unknown fields, so both particle-generation paths read a default position and spawned particles at world origin. The override removes that conflicting room field rather than inventing a replacement. `compat-imports/Vector.proto` is a build-only dependency stub; the merged schema retains the full base Vector descriptor. Captured-packet and real scene-spawn tests pin the observed coordinates, rotation and particle counts.

Achievement claims use native 7.1 request command 25857 and response command 9071. `TakeAchievementRewardReq.proto` overrides achievement IDs from stale field 10 to packed field 15; protobuf also accepts the unpacked form. A captured claim for achievement 82041 is `7a03f98005`. `TakeAchievementRewardRsp.proto` overrides retcode from field 5 to 1, IDs from 12 to 8, and ItemParam messages from 13 to 11. ItemParam remains ordinary uint32 item ID/count on fields 1/2. A successful response for that ID and item 201 × 5 is `4203f980055a0508c9011005`. The handler validates the entire bounded request and batch before calling the existing guarded reward boundary; it does not change eligibility, persistence or delivery semantics.

`ChooseCurAvatarTeamRsp.proto` fixes command 29488's current-team field from 10 to 5 and signed int32 retcode from 11 to 12. The command ID is already mapped upstream; the stale field numbers still let the client interpret a successful first deployment as the wrong/default team. Team 2's success payload is `2802`; retcode -1 is `60ffffffffffffffffff01`. Request routing and team mutation remain unchanged.

These corrections are pinned by native getter/reader/tag/value-flow evidence and in-game claim/team-switch verification. `AchievementClaimProtocolTest` covers captured request routing, packed/unpacked IDs, full-message validation, limits, batch eligibility, retries and actual response bytes. `TeamSwitchResponseProtocolTest` checks the first acknowledgement through the real send boundary using an in-memory transport. Tests start no game server and modify no real player records.

`TakePlayerLevelRewardReq.proto` overrides the stale Adventure Rank request descriptor: `level` is uint32 field 15, not field 11. Captured 7.1 Katheryne requests for levels 2, 3 and 4 are `7802`, `7803` and `7804`. `AdventureRankRequestSchemaTest` pins the descriptor and separately verifies decoding and encoding against those bytes. This brings generated messages into agreement with the existing field-15 handler; opcode, full-payload validation and reward protections remain unchanged.

`PlatformStartRouteNotify.proto`, `PlatformStopRouteNotify.proto` and `PlatformChangeRouteNotify.proto` carry the 7.1 field numbers from kitkat-multiverse/genshin-protocol 7.1.0 (platform/entity/scene time on 7/2/11, 12/5/14 and 4/6/7), for CmdIds 29891, 4699 and 6989. The same dump's 7.0 names match the known 7.0 CmdIds 24148, 21414 and 28611. `PlatformInfo` itself is unchanged from the base descriptor, and `compat-imports/PlatformInfo.proto` is only an import stub.

`TpsEquipChangeNotify.proto` imports `SceneWeaponInfo.proto`, which already exists inside the base descriptor set. `protocol/7.1/compat-imports` provides a build-only empty `SceneWeaponInfo` declaration so protoc can parse the recovered source. Protoc writes the recovered source files to a supplemental descriptor set without `--include_imports`, so this import stub never enters the combined descriptor set.

`ProtocolJavaGenerator` parses both descriptor sets and merges files by proto file name. Supplemental files replace a base descriptor only when they use the same file name. Before code generation, the generator also restores TPS semantics on six wire slots that already exist in the base descriptor under obfuscated names: `AvatarInfo.tps_weapon_list` field 37, `SceneAvatarInfo.tps_weapon_list` field 31, `SceneTeamAvatar.tps_weapon_list` field 382, `AvatarEnterSceneInfo.tps_weapon_list` field 13, `SceneWeaponInfo.ammunition_list` field 12, and `_TpsWeapon.accessory_id_list` field 2. Each replacement validates the old field number, label, wire type, and message type before changing the descriptor. Generation fails if the captured descriptor shape differs from the expected 7.1 shape.

`generateProtocolJava` uses protoc 4.36.2 to regenerate the combined base descriptors and recovered additions into `build/generated/sources/protocol/7.1/java/main`. Normal `compileJava`, `jar`, and `sourcesJar` builds depend on this task. The generated code is compiled against protobuf-java 4.36.2 from the main build.

`lintGeneratedProtocolJava` compiles only regenerated protocol sources with `-Xlint:all -Werror`. This keeps generated-code warning regressions separate from handwritten warning debt.

`ProtocolGenerationTest` checks a protobuf round trip, base descriptor dependencies, recovered TPS descriptors, and the six restored TPS field numbers. The protocol-generation workflow runs this test and the generated-source lint gate on Linux and Windows.

The recovered `WeaponUpgradeReq.proto` and `CalcWeaponUpgradeReturnItemsReq.proto` override the stale request descriptors. The 7.1 upgrade request uses opcode 21801 with target GUID field 5, consumed weapon GUIDs field 15 and materials field 8; the preview uses opcode 7145 with fields 1, 14 and 10 respectively. `compat-imports/ItemParam.proto` is only an import stub; the canonical descriptor retains item ID field 1 and count field 2. `WeaponUpgradeRequestTest` uses native wire fixtures and the real request handlers to check decoding, material consumption, levels and refunds.

The checked-in generated Java dump is legacy material and is not a protocol source of truth. Future protocol recovery should update the canonical descriptor set or the recovered `.proto` additions and regenerate Java instead of editing generated Java by hand.
